# 🔄 Topic

I found a subtle integrity problem in a local capture job that extracts dated commitments from message windows. When the model returned an empty or unparseable result, the job still advanced its watermark. The next run then treated those messages as already seen, even though nothing had successfully read them.

That is not only a reliability bug. In a security workflow, silently moving the evidence boundary can create an audit gap: the system appears to have processed a record when it has only skipped it.

# 🎯 Goal

Make the capture job fail safely when extraction fails, while preventing one permanently unreadable window from blocking every later message forever.

# 🛠 What I Did

The real defect appeared after three extraction attempts returned zero characters. One affected window contained fourteen messages. The old code moved the watermark anyway, so the messages disappeared from the next candidate set without a durable explanation beyond a log line.

I changed the state transition:

```text
successful parse  → apply valid actions and advance the watermark
failed parse       → keep the watermark, record a retry, and inspect again later
three failures     → log the decision and release that one poisoned window
```

The implementation tracks unreadable chats separately. A successful parse clears the retry count. A model or parsing failure leaves the watermark unchanged. After the configured retry limit, the job records that it is giving up on that window so one bad input cannot stop all future work.

I added tests for the state shapes and used perturbation checks: removing the failure record made two of the three new tests fail. The deployed capture script was then checked byte-for-byte against the repository version, and a real dry run with no new work completed without the earlier `KeyError`.

# 🔗 Key Cybersecurity Connections

## 🔍 Investigation Questions

When a security pipeline says that it processed a record, I should ask:

1. Did the parser actually produce a valid result?
2. Did the state cursor move only after that result passed validation?
3. If processing failed, can the same input be retried?
4. Is there a bounded escape path for a poison record?
5. Can an operator distinguish a quiet period from repeated processing failure?

## 🚨 Detection Opportunities

Useful signals include repeated parse failures, an unchanged watermark across several runs, a sudden drop in extracted records, and a `giving up` event after the retry limit. These signals do not prove malicious activity, but they identify a loss-of-visibility condition that deserves attention.

## 🧭 MITRE ATT&CK Techniques

No direct ATT&CK technique mapping is claimed. This is a defensive data-integrity and observability lesson, not an attribution of attacker behaviour.

# ⚠️ Limitations

The work concerned a local owner-controlled automation path and synthetic extraction checks. I am not claiming that it monitored an enterprise SIEM or handled production incident evidence. The security lesson is about preserving honest state transitions in any pipeline that turns messages or logs into actions.

# 📚 What I Learned

An empty result is not the same as a completed result with zero findings. Those states must be represented differently. Advancing a cursor is itself a consequential action: it says that everything before that point has been handled or deliberately accounted for.

# 🧩 Lessons Learned

- Advance evidence boundaries only after successful validation.
- Preserve failed input long enough to retry it.
- Bound retries so one poison record cannot create permanent denial of service.
- Make quiet runs, failed runs, and skipped runs distinguishable in logs.
- Test the failure path, not only the happy path.

# 😄 TL;DR

I fixed a capture job that could mark unreadable messages as seen. The safer design keeps the watermark in place after a failed extraction, retries the input, and logs a bounded escape decision instead of silently losing evidence.
