# 🔄 Topic

I reviewed a three-turn image-history exercise from the previous day's isolated-worker work. It tested whether two pictures survived persistence and remained available to a later text-only turn, while keeping the complete inference request within explicit limits.

# 🎯 Goal

Accepting one small input does not prove that a conversation remains bounded. Earlier images can accumulate in restored history, and each request can carry more data than the newest message suggests.

# 🛠 What I Investigated

The persistence path could flatten image content into a screenshot placeholder. That may preserve a readable transcript, but it cannot preserve the image itself for a later inference request.

The candidate used a process-local wrapper around the native persistence row builder for one exact agent object. It preserved only validated user image parts, retained the other native row fields, refused incompatible content overrides, and restored the original builder when the scope ended.

The recorded exercise followed this sequence:

| Turn | New input | Image occurrences received by the synthetic inference backend |
|---|---|---|
| 1 | First picture | 1 |
| 2 | Second picture | 2 |
| 3 | Text follow-up | 2 |

The result recorded three durable answers and two retained images. This established that the tested path preserved the image representations across turns. The responses were synthetic, so it did not establish visual reasoning quality.

# 🔗 Key Cybersecurity Connections

The request validator counted every image occurrence and the cumulative length of its encoded representation. Reusing the same object did not make repeated occurrences free.

For this exercise, the request budget allowed at most four image occurrences and 393,216 encoded image characters. The separate 524,288-byte broker frame limit still applied to the complete request. Text, tool data, JSON structure, and encoding overhead could therefore make a request fail before its image budget was exhausted.

The refusal checks covered a fifth occurrence, aggregate encoded overflow, and an otherwise approved image placed outside the accepted user-content structure. They also checked that the complete frame remained bounded. Those checks tested the admission contract rather than merely demonstrating that a small example worked.

# ⚠ Challenges

Silently removing old pictures would have made the request smaller while changing the question the model could answer. The tested overflow behavior refused the request instead of stripping history to manufacture a successful inference.

I also had to separate request capacity from data retention. A request-size limit says nothing by itself about how long image data remains in a database, backup, or archive. Preserving images creates a separate privacy and deletion question.

# 🚨 Detection Opportunities

An operator could monitor image-occurrence counts, encoded-size totals, frame-size refusals, and whether persistence retained the expected content type. Routine logs should describe these properties without reproducing the pictures.

# 📚 What I Learned

Persistence, restoration, and request admission form one chain. A correct first turn can still conceal a broken follow-up if a storage layer replaces meaningful content or a request builder forgets to budget for history.

# ➡ Next Steps

Review retention, backup, and deletion behavior separately, and test installed conversation handling before claiming operational readiness. The archived exercise recorded no real sends, no external network activity, and no production change.

# 😄 TL;DR

The three-turn exercise preserved two images and enforced aggregate request limits. It demonstrated bounded candidate behavior, with retention policy and live acceptance still separate.
