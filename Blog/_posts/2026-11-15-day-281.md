# 🔄 Topic

An encrypted backup can contain the data I expect and still lack code needed to use it. During the Ubuntu migration, a real recovery exercise exposed an imported snapshot loader missing from the memory backup.

# 🎯 Goal

Check whether the restored memory artifacts could support an actual search, beyond proving that files were present and their hashes matched.

Earlier backup work covered consistency, snapshot presence, and stale mirrors. This exercise added a different question: does the recovery set include the application dependencies that connect the restored data to a working result?

# 🛠 What I Did

The memory recovery set included the pinned snapshot, launcher, search code, embedding model, service definition, dependency list, and recovery metadata. The restore exercise found that the search code also imported a separate snapshot loader. That module had not been included.

I added the loader to the explicit backup inventory. The corresponding regression test removes it from a temporary fixture and expects backup preparation to refuse the incomplete set. That makes this particular omission visible before another recovery attempt.

A second correction concerned Python version metadata. A virtual environment's interpreter can be a symlink. Resolving that link before looking for `pyvenv.cfg` led away from the environment whose version I needed to record. The fix retained the interpreter's virtual-environment path for that metadata lookup.

# 🔍 What the Recovery Evidence Showed

The recorded encrypted restore checked exact paths, file hashes, and SQLite integrity. A separate selective restore of the memory artifacts then used the restored code and model to search the restored snapshot. It returned five results, while a deliberately corrupted vector copy was rejected. Temporary restore material was cleaned up.

Those checks answer different questions:

- Path and hash checks establish that the selected files were recovered as expected.
- SQLite checks examine the restored database's integrity.
- A search exercises the connection between the restored code, model, and data.
- Corruption rejection checks a failure path rather than only a successful read.

# 🔗 Key Cybersecurity Connections

This is recovery readiness and integrity validation. Encryption protects stored backup contents, but it cannot make an incomplete application recoverable. A dependency inventory needs to follow what the application actually loads.

The missing-module test covers one known omission. It does not automatically discover every future import or prove that the dependency inventory will stay complete as the application changes.

# ⚠ Evidence Limits

The selective restore reused existing runtime dependencies. I did not prove a fresh virtual-environment rebuild on an empty machine. The Ubuntu backup was also on the server's own disk, so this result does not establish protection against loss of that disk.

Authentication recovery remained a separate decision. A successful memory search did not prove that every external integration could authenticate after total loss.

# 📚 What I Learned

I need both byte-level recovery checks and a bounded application operation. The operation can expose a missing dependency that a correct archive manifest cannot reveal on its own.

# ➡ Next Steps

A future clean-machine drill should rebuild the runtime from the recorded requirements and repeat the search. Off-disk recovery needs its own evidence too.

# 😄 TL;DR

A real restore found a missing imported module. I added it to the backup inventory, corrected Python environment metadata, and kept the successful search separate from the still-unproven clean-machine rebuild.
