# 🔄 Topic

A delegated request reached a coding agent with its caption but without the attached picture. I reviewed the repair that carried the image through the server-to-laptop relay and preserved it until the agent could read it.

# 🎯 Goal

Keep the request and its actual attachment together. An agent receiving instructions to inspect a picture should either receive that picture or get a clear refusal before the job starts.

# 🛠 What Changed

The receiving plugin selects downloaded images from the current event. It does not search a shared directory for the latest photograph, which could attach an unrelated image. Task-local attachment context is reset for the next turn so an earlier picture is not silently reused.

A filesystem path on the receiving server is not a usable attachment on another computer. The relay therefore transports encoded image bytes and stages private temporary files on the destination. The installed launcher snapshots the files before starting a worker or saving a proposal that may be confirmed later.

That last step matters because a temporary download may disappear while a proposal waits. The worker needs a durable snapshot belonging to its request, rather than a path whose lifetime ended before confirmation.

The two coding-agent interfaces receive attachments differently: one uses native image arguments; the other receives readable snapshot paths with instructions to open them. Passing an argument is only one part of the contract. The referenced bytes must still exist when the worker reads them.

# 🔒 Validation and Privacy

The relay limits the batch to eight images and ten mebibytes of decoded image data in total. It checks supported file signatures and rejects malformed payloads. A signature check is an admission check, not proof that an image is safe for every decoder.

Private staging and snapshots restrict file access. The recorded launcher checks verified file permissions of 600 and image-directory permissions of 700. Temporary relay copies are cleaned after the launcher takes its snapshot; that cleanup does not by itself define the retention period for the durable copy.

The plugin also detects a message that declares an image attachment but has no downloaded image. It refuses that handoff instead of launching a text-only job that appears complete. Existing owner, direct-message, and forwarded-message restrictions remain separate controls.

# 🧪 What Was Verified

The 22 November verification record reports launcher, relay, and plugin suites passing. Those checks include reading exact bytes after the original file is removed, preserving a proposal attachment until confirmation, rejecting unavailable images, and resetting attachment context between turns.

A recorded installed-path exercise sent a synthetic image through the server plugin, relay, and laptop launcher. Its persisted snapshot matched the expected hash. No model call or Telegram send was part of that exercise.

For this article I inspected the implementation, tests, and deployment record. I did not repeat that live exercise or ask a model to interpret a new photograph.

# 📚 What I Learned

A successful job launch does not prove that all inputs arrived. For attachments, I need evidence for selection, byte transport, readable storage, lifetime, and refusal when the input is missing.

The transport result is useful without overstating it: the recorded exercise proved attachment delivery to the launcher, while actual visual interpretation remains a separate outcome.

# 😄 TL;DR

I reviewed a deployed repair that preserves current-request photos across a machine boundary and delayed confirmation. Missing downloads stop the handoff; exact-byte checks establish transport, not vision quality.
