# 🔄 Failing Safely When the Voice Backend Is Offline

I worked on a failure mode where Hermes could be available on Ubuntu while the Mac voice synthesizer was not. The security lesson was simple: an unavailable dependency must produce an explicit, bounded result rather than an ambiguous retry or a claim that a spoken reply was delivered.

# 🎯 Goal

The goal was to detect the unavailable voice backend before starting synthesis, return a clear failure state, and preserve the text path when that was allowed. The system should not hang, duplicate work, or report success because a subprocess was launched.

# 🛠 What I Did

I added a fail-fast check before Mac voice synthesis and wrote focused tests for the offline path. The tests cover the unavailable backend, the text fallback, subprocess cleanup, and the rule that no successful voice receipt is created when synthesis never became possible.

The deployed checkpoint also records that the Mac-offline condition was observed. That is different from testing only a mocked function: the design starts with the real dependency boundary, then uses controlled tests to exercise the failure cases repeatedly.

# 🔗 Key Cybersecurity Connections

Availability is a security property. A stuck or misleading fallback can cause operators to miss alerts, repeat an action, or trust a notification that never reached its intended channel. Fail-fast behavior reduces the time spent in an uncertain state.

## 🔍 Investigation Questions

- Was the voice backend reachable before synthesis began?
- Did the process exit and clean up its temporary resources?
- Was a text fallback actually selected, or merely planned?
- Is the final receipt tied to the channel that succeeded?

## 🚨 Detection Opportunities

Audit records should distinguish `voice_unavailable`, `text_fallback`, `synthesis_failed`, and `voice_delivered`. Collapsing them into one “reply sent” label hides the exact failure an incident reviewer needs.

# ⚠ Challenges

It is tempting to treat a process launch as progress. It is not proof of output. The check had to happen before synthesis, while the cleanup path had to handle a subprocess that exited, timed out, or never became reachable.

# 📚 What I Learned

Graceful degradation is not the same as silent degradation. A secure fallback tells the operator what happened, uses only an allowed alternative, and leaves a receipt that cannot be mistaken for delivery on the original channel.

# 🧠 Reflection

When a system spans two machines, “the service is up” is too vague. I need to ask which dependency, which channel, and which evidence are actually available.
