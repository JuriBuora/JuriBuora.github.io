# 🔄 Separating an Admission Receipt From Authorization

I examined the native Telegram update path and found a distinction that is easy to miss: a callback receipt can prove that code observed an event, but it does not automatically prove that the event was authorized, durably admitted, or answered.

# 🎯 Goal

The goal was to test the meaning of native receipts without changing the production poller or sending real messages.

# 🛠 What I Did

Using recording transports and synthetic updates, I tested duplicate callbacks, error observers, and a consumer-free updater. The updater advanced its next polling offset even though the queue still contained the earlier update. The receipt file preserved update IDs, but not the original transport provenance or proof of a completed reply.

Mutants that weakened duplicate handling were rejected. The workload completed with no external network, inference, or real sends.

# 🔗 Key Cybersecurity Connections

This is an authorization and audit-integrity problem. Logging that an event reached a handler is weaker than proving that the current authorized receiver admitted it before acknowledging the source.

## 🚨 Detection Opportunities

Audit records should distinguish received, authorized, durably admitted, dispatched, completed, and delivered. Collapsing these into one `accepted` flag hides where an event actually stopped.

# ⚠ Challenges

The test was deliberately bounded. It did not prove the full installed handler, live authentication, or production data-loss behaviour.

# 📚 What I Learned

An audit receipt is evidence with a scope. Before relying on it, I must ask what source identity, authorization decision, cursor, and completion state it actually binds.

# 😄 TL;DR

An event receipt is not automatically an authorization grant or a delivery receipt.
