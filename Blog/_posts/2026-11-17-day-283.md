# 🔄 Topic

A recovery drill found that killing an update process could leave its temporary validation worker running. I reviewed the resulting fix and the checks around the interrupted memory-snapshot update.

# 🎯 Goal

Keep an interrupted candidate update from changing the active snapshot or leaving a temporary service behind. Both persistent state and running processes belong in that verification boundary.

# 🛠 What I Reviewed

Before applying a new memory snapshot, the updater starts a temporary loopback worker and checks that the candidate can answer using the pinned local data. Ordinary cleanup terminates that worker when the validation call finishes.

The recorded drill exposed a different path: the updater was forcibly killed during candidate validation, leaving the worker alive. The fix added a Linux parent-death signal request to the child startup path, using `PR_SET_PDEATHSIG` with `SIGTERM`.

The Linux manual describes this as a signal requested for subsequent termination of the parent thread. It also documents important limits, including the case where the parent has already terminated before the request is made. I treat it as a specific lifecycle mechanism, with checks around it, rather than a universal guarantee that descendants cannot survive. [Linux man-pages: PR_SET_PDEATHSIG](https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html)

# 🔍 How the Drill Defines Success

The drill creates a scratch snapshot root seeded from a copy of the active release. Its injected restart and live-check operations refuse to run, keeping those transitions outside the exercise.

For the interruption case, it stages a candidate, kills the apply process during validation, and checks that the previous snapshot remains selected and verifiable. It also checks whether the update lock can be acquired again and whether a matching candidate worker remains running.

Other cases deliberately corrupt a candidate and check refusal before selection, then corrupt the scratch current release and exercise fallback to a previous release through a real launcher subprocess. The final checks include restored-copy hashes, the unchanged live selection, and removal of scratch files.

These are distinct observations. An unchanged pointer does not show that a worker exited. A released lock does not show that the previous release can answer. A deleted directory does not show that no process still references its contents.

# 🔗 Key Cybersecurity Connections

This is process lifecycle and recovery integrity. A temporary worker may retain access to data or keep a listening socket after its initiating operation ends. Even on loopback, its lifetime should match the bounded operation that created it.

The useful security question is concrete: after interruption, what state and processes remain? No attacker activity or direct ATT&CK mapping is claimed here.

# ⚠ Evidence Limits

The fix commit records the orphan found by the drill. I inspected the implementation and its result evaluator for this write-up; I did not repeat a forced interruption of a deployed service.

The evaluator treats a missing check as failure and requires the orphan-process result to be explicitly false. Its fixture tests validate that decision logic. Those fixture results alone do not establish every possible operating-system timing or prove that every future child process inherits the same protection.

# 📚 What I Learned

Crash recovery must account for temporary workers as well as files and pointers. Cleanup needs observable checks after interruption, especially when the interrupted process cannot execute its normal cleanup path.

# 😄 TL;DR

A forced-interruption drill exposed an orphaned validation worker. The fix tied its lifetime to the parent, while the drill separately checks the old snapshot, lock release, remaining processes, and scratch cleanup.
