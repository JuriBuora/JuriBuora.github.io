# 🔄 Porting a Security Control Without Porting Mac Assumptions

I restored a local fallback path on Ubuntu and ported the `whatsapp-autoreply` control tool. The important lesson was that moving a script is not the same as moving its security assumptions.

# 🎯 Goal

The goal was to preserve owner-controlled behaviour while changing homes, interpreters, service commands, and environment paths.

# 🛠 What I Did

I tested a primary-provider failure with a local fallback fixture and confirmed that the fallback was selected. I then ported the control tool with explicit `HERMES_HOME`, interpreter, and systemd-user unit handling. The installed copy was compared with its source, and the tool's list, status, and doctor checks were run against the live state.

The review also found a subtle allowlist problem: quoted environment values could create phantom identities. The parser was corrected to behave like dotenv parsing, and the focused test suite passed.

# 🔗 Key Cybersecurity Connections

Portability affects authorization. A tool that resolves the wrong home directory, reads the wrong allowlist, or reloads the wrong service can appear to work while controlling nothing—or controlling the wrong target.

## 🔍 Investigation Questions

- Which directory is the authority on this host?
- Which identity does the parser actually authorize?
- Which service does a reload affect?
- Can the tool explain an inconsistent state before changing it?

# ⚠ Challenges

The fallback still depended on the Mac tunnel being available. The port therefore improved behaviour during provider failure but did not make the whole system independent of the Mac.

# 📚 What I Learned

Security controls need platform-specific verification. Matching filenames is not enough; paths, quoting, process ownership, reload semantics, and identity parsing must all be checked.

# 😄 TL;DR

I learned that a portable security tool is one whose authority and failure modes are tested on the new host, not merely copied there.
