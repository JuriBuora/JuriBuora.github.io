# 🔄 Topic

A repair worker that cannot authenticate has a different problem from a worker that produced an incorrect patch. I reviewed how the recovery state machine records that distinction and waits for an operator instead of repeatedly launching more attempts.

# 🎯 Goal

Preserve the original task and the failed attempt's evidence while making the missing external prerequisite visible. Restarting the gateway should not turn a parked authentication problem into another automatic launch.

# 🛠 What I Reviewed

The recovery implementation has a `BLOCKED_EXTERNAL` state with a stored reason and an operator action. An attempt classified as an authentication or quota problem can enter that state rather than being reported as a failed code repair.

The ordinary recovery ticker does not advance that authentication block. The operator must resolve the prerequisite and explicitly unblock the task. Both unblocks and worker attempts have limits; a repeated login failure does not create an unlimited retry budget.

The attempt ledger records separate worker runs. That preserves the distinction between an earlier unsuccessful code attempt, an authentication block, and a later attempt launched after intervention.

# 🧪 How the Fixture Exercises the Failure

The inspected integration fixture uses the real recovery module, real temporary Git worktrees, and a real verifier command. Its launcher is a stub. The fixture writes a synthetic “not logged in” error into the worker's output and checks the resulting state.

It then advances multiple ticks and reconciles the stored task through a newly opened state store. The expected result is no additional worker launch while the authentication block remains. After an explicit unblock, the fixture checks that one fresh attempt starts.

The dated production-readiness record reports this fixture path as executed. I inspected its code and recorded results for the article; I did not invalidate a real login, consume a paid worker attempt, or send a test message to another person.

# 🔍 The Reason Determines How Work Resumes

Not every external block should restart the same kind of work. An unsafe Git integration can hold an already verified candidate; resolving that condition should retry integration rather than ask the agent to rewrite the patch.

Human promotion has another rule. Under the latest policy, a task waiting for a verified commit to reach the working branch cannot be released with the generic unblock command. It waits for a read-only promotion check to confirm the required ancestry.

That prevents “blocked” from becoming a vague status with one button that bypasses every boundary. The stored reason needs to select the permitted next transition.

# 🔗 Key Cybersecurity Connections

This combines availability, bounded resource use, and authorization. Retry logic should not invent permission to fix an external prerequisite or move a repair into production. A durable pause can preserve the work without widening the worker's authority.

Operator visibility also matters. A useful block report identifies the prerequisite and next action without exposing credentials, session keys, or private worker prompts.

# ⚠ Evidence Limits

The login failure was synthetic. The fixture shows how the tested classifier and state transitions respond to that input; it does not prove that every provider error will be classified correctly.

Cancellation also has a documented limit: cancelling a recovery does not necessarily kill a running worker on the Mac. Ignoring its later result and stopping its process are separate outcomes.

# 📚 What I Learned

A recovery system needs meaningful waiting states, durable reasons, and bounded ways to resume. Repeating the same unavailable operation is not evidence that recovery is progressing.

# 😄 TL;DR

I reviewed a synthetic login-failure exercise that parks recovery across ticks and reconciliation. Authentication unblock, integration retry, and human promotion each retain their own transition rules.
