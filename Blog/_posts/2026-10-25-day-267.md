# 🔄 Recovering LaunchAgents Without Trusting a Broken Runtime

An update to Homebrew Python caused macOS LaunchAgents to disappear from service. That looked like an availability issue, but it also had a security dimension: a recovery mechanism must not blindly re-register arbitrary files just because a service is missing.

# 🎯 Goal

The goal was to detect the broken registration, verify the intended source and code-signing state, and re-register only the known LaunchAgents that matched the expected inventory.

# 🛠 What I Did

I added a LaunchAgent code-sign guard and tests around the recovery path. The guard checks the expected service definitions and records what it is doing. The related backup work also records the source file, error number, and error text when a phase fails, so an operator can distinguish a missing registration from a damaged or unreadable executable.

# 🔗 Key Cybersecurity Connections

Service recovery is a supply-chain and persistence boundary. Launching a similarly named script from an unexpected path could restore availability while introducing an integrity problem. Recovery needs identity checks, not only existence checks.

## 🚨 Detection Opportunities

Monitor for a service whose label, executable path, signature state, or source hash changes unexpectedly. A recovery alert should say whether the action was a re-registration, a refusal, or an unresolved state.

# ⚠ Challenges

The failure happened after an environment change rather than an obvious code defect. That makes provenance important: the guard needs to show which source was reviewed and which runtime was actually restored.

# 📚 What I Learned

Availability tooling can become a persistence mechanism if its authority is too broad. The recovery path should be narrower than the service it repairs.

# 🧠 Reflection

The safest repair was not “make every missing service start.” It was “recognize this exact service, verify its source, and refuse ambiguity.”
