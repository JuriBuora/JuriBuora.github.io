# 🔄 Topic

Backups are often described as an availability control, but they also protect security evidence and recovery capability. A backup job can remain installed and scheduled while quietly failing for several nights. If nobody notices, the organisation may discover the gap only after data or logs are needed.

I investigated a local backup alert showing that the Ubuntu server had been unreachable over the private network. The important part was not merely bringing the host back. It was proving what the next successful backup actually contained.

# 🎯 Goal

Separate “the backup command ran” from “a usable snapshot was created and can be identified,” while keeping secrets out of the report.

# 🛠 What I Observed

The error log recorded repeated `ubuntu-server unreachable` failures, and the last known good snapshot was several days old. That meant the schedule existed but the recovery point objective was already being missed.

After connectivity returned, I ran the backup and recorded its receipt identifier. I then checked the snapshot manifest for the expected categories of state: authentication metadata, configuration, credential storage, and the local state database. I reported only their presence, not their contents.

This gave me three separate facts:

1. the previous scheduled attempts had failed;
2. a later manual run created a named snapshot and receipt;
3. the receipt referenced the expected state files.

Those facts are stronger than a green process exit by itself. They still do not prove a full restore, so I am not claiming restore readiness from this check alone.

# 🔗 Key Cybersecurity Connections

## 🔍 Investigation Questions

For a security-relevant backup, I should ask:

1. When was the last verified successful snapshot?
2. Is the job failing because of the source, network, permissions, or destination?
3. Can I identify the exact snapshot and receipt for the run?
4. Does the snapshot contain the state needed for recovery and investigation?
5. Has a restore been tested separately?

## 🚨 Detection Opportunities

Useful alerts include consecutive failed runs, an age threshold for the newest verified snapshot, a missing receipt, a manifest that lacks required state categories, and a snapshot whose hash or size changes unexpectedly. A backup alert should be treated as a security signal when the missing data includes logs, identity state, or recovery configuration.

## 🧭 MITRE ATT&CK Techniques

No direct ATT&CK technique mapping is claimed. Backups can affect recovery from many incidents, but a failed backup alone does not identify attacker behaviour.

# ⚠️ Limitations

I verified the new snapshot receipt and the presence of expected files by manifest, while keeping private contents out of this post. I did not perform a destructive restore or claim that the files were complete, uncorrupted, or sufficient to rebuild the entire system.

# 📚 What I Learned

Observability has to cover the outcome that matters. “The timer fired” is not the same as “the recovery point exists.” A security-minded backup check should expose age, identity, expected contents, and restore status as separate evidence fields.

# 🧩 Lessons Learned

- A scheduled job can be healthy in configuration and failing in reality.
- Repeated backup failures create an evidence and recovery gap.
- A receipt makes a snapshot referencable; a manifest makes its scope inspectable.
- Presence checks are useful, but they are not restore tests.
- Never publish the contents of authentication or credential files to prove they exist.

# 😄 TL;DR

I investigated three nights of backup failures, then verified a fresh snapshot by receipt and expected-file presence. The remaining boundary is clear: only a separate, safe restore test could prove recoverability.
